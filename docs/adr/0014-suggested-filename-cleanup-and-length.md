# 建議檔名：清理頁面標題的樣板後綴 ＋ 可選長度上限，伺服器另設 byte 安全帶

偵測完成後，前端會把該次 Detection Session 的頁面 `<title>` 當作每個 Candidate 檔名輸入框的預設值。實務上頁面標題幾乎都帶樣板後綴（`實際標題 - 頻道 - YouTube`、`實際標題 ｜ 站名`⋯），塞進輸入框後又長又雜，使用者每次都要手動刪一段。

決定把這件事拆成三塊、各司其職：

1. **樣板後綴清理（前端，屬美觀問題）**：以「前後至少一個空白」的分隔符 `-`／`–`／`—`／`|`／`｜`／`:`／`：` 切分清理後的標題，若切出 ≥ 2 段就**只丟掉最後一段**，其餘用 ` - ` 統一接回（不還原原本的分隔符，省事且輸出一致）。接著壓多重空白、去頭尾的空白與 `.`／`-`。清理後為空則退回原始標題，再退回通用名稱 `download`。

2. **可選長度上限（前端，屬美觀問題）**：Settings 新增 `suggestedFilenameMaxLength`，以**字元**計（`Array.from` 長度，正確處理 CJK 與 emoji），只裁 base、副檔名永遠完整保留。超過上限時在字數內的**最後一個空白處**切，找不到空白才硬切；不加省略號。未設定／`0`／留白 = 不套用上限（清理邏輯仍照跑）。預設 `80`；有值時下限 `10`。API 上以 `null` 表示關閉，DB 存 `0` 當 sentinel。

3. **byte 安全帶（伺服器，屬「別壞掉」問題）**：`sanitizeFilename()` 對使用者**最終送出**的檔名（不論來自建議值或手打）加一道以 byte 計的硬上限——base ＋ 副檔名總長 ≤ 200 bytes，超過就靜默裁短 base（切在字元邊界、不斷 UTF-8 序列），比照現有 sanitize「靜默清理、不回 4xx」的風格。255 是多數檔案系統的單檔名 byte 上限，留 55 bytes headroom 給 two-phase landing 的 `source`／`.mkv` 改名／目的地既有檔衝突時可能加的後綴。

美觀層（字元、前端、可關閉）與安全層（byte、伺服器、永遠生效）刻意分開：前者服務「使用者讀不完、難編輯」，後者服務「`moving` 階段 `ENAMETOOLONG` 讓 job 失敗」，兩者的正確單位與生效時機都不同，混在一起會兩邊都做不好。

## Considered options

- **只加設定 + 從尾端硬砍**（使用者原始提案）：實作最小，但砍出來的檔名常是把標題砍一半、尾巴還黏著半個站名，因為沒有處理「雜訊在尾segment」這個真正的成因。
- **完全不加設定，只做清理**：這不是每台部署會有不同取捨的旋鈕，本來傾向如此；最後仍加設定，是因為清理後偶有例外的超長標題，給個溫和上限成本低。
- **更積極的啟發式**：只留第一段（標題含破折號時誤砍成兩三個字）、或從尾端逐段砍「短且像樣板」的段（最難預期）。都因為誤砍時使用者會困惑「為什麼檔名只剩這樣」而放棄，選了誤砍成本最低的「只丟最後一段」。
- **伺服器對超長檔名回 400 擋下**：與現有 `sanitizeFilename` 一路靜默清理的行為不一致，且使用者面對的是一個他多半沒細看的建議值，擋下來只會讓人不知所措。

## Consequences

- `app.js` 的 `sanitizeForFilename`／`backfillDefaultFilenames` 一帶多出清理與截斷邏輯，仍是裸函式、無測試（該檔目前零測試，不為此引進 test harness）。
- 標題本身就含分隔符時（`前傳 - 第一章 - 站名`）會被砍成 `前傳 - 第一章`——可接受，欄位可改。
- `SettingsStore`／`GET`＋`PUT /api/settings`／Settings 表單三處各加一個欄位，`null` ↔ 空字串 ↔ DB `0` 的轉換要一致。
- `app.test.ts` 補一個 case：手打超長檔名（含中文）→ job 的 `filename` ≤ 200 bytes、副檔名完整、無斷碼。
- 既有部署升級後 `suggestedFilenameMaxLength` 不存在 → 取預設 `80`，建議檔名會比升級前短，屬預期內的改善。
