# 刪除下載紀錄：重用取消 API，只清 DB，不動磁碟

歷史紀錄表格（`GET /api/downloads` 驅動）目前只能瀏覽，沒辦法把已經結束的紀錄清掉。新增刪除功能，範圍限定在終態的 Download Job：`completed`、`failed`、`cancelled`。`queued` 已經有 ADR-0009 定義的「取消排隊」，`pending`/`downloading`/`moving`（進行中）目前沒有任何中止機制，這次也不處理——刪除紀錄純粹是清「已經結束的事」，不涉及中止一個正在進行的操作。

刪除只清 DB 裡的那筆 `download_jobs` row，**不動磁碟**：`completed` 的 `outputPath` 指向的檔案、`failed` 可能留在 `CACHE_DIR` 底下的殘留（ADR-0005 提過的既有限制——搬移失敗時 cache 檔案不會自動清、也沒有自動重試）都不處理。刪除紀錄只是讓使用者不用再看到這筆歷史，跟「這個檔案我還要不要」是兩件事，使用者要清檔案本來就有檔案總管或直接進容器/掛載點操作，沒必要在這支 API 裡幫使用者做決定。

API 層重用 ADR-0009 已經有的 `DELETE /api/downloads/:id`，依 Download Job 當下狀態分流：`queued` 走既有的取消（`UPDATE` 成 `cancelled`）；終態走新的刪除（真正 `DELETE FROM` 該筆 row）；`pending`/`downloading`/`moving` 回 `409`（兩種語意都不適用）；未知 id 回 `404`。前端沿用同一個 fetch 呼叫，只是依所在情境（active-downloads-list 的排隊列 vs. history 表格的終態列）顯示不同按鈕文字（「取消」vs.「刪除」），語意上刻意不讓使用者混淆——按鈕文字分開講，但底層就是同一個「我不要這筆了」的動作。

歷史表格同時支援單筆刪除（每列一顆按鈕）跟批次刪除（終態列前加 checkbox + 表頭全選 + 「刪除選取項目 (N)」按鈕）。批次不開專門的 batch API，前端對每個勾選的 id 各自呼叫上述同一支單筆 `DELETE`，選幾筆送幾個請求。

## Considered options

- **刪除紀錄時順便清掉磁碟上的檔案**：對使用者來說可能更直覺（「刪除」聽起來就該把東西真的清掉），但風險高很多——尤其 `DOWNLOADS_DIR` 常指向 NFS（ADR-0005），一個誤觸的刪除鈕就會真的弄丟已經下載好的影片，而且 `failed` 的殘留清理涉及判斷檔案是否還在使用中等更複雜的狀態，這次選擇不做，把「刪紀錄」跟「刪檔案」拆成兩件事。
- **開一支獨立的 batch DELETE API**（例如 body 帶一串 `ids`）：一次 HTTP 請求處理完，但要多設計「部分成功怎麼回報」的格式（例如某幾筆 id 已經被刪或狀態不對時），對單人自架工具、選取筆數不會太多的情境來說，複雜度大於好處。
- **刪除跟取消做成兩個獨立的動作/API**：語意上更乾淨（一個動詞對應一個 HTTP 方法），但對使用者來說「取消排隊中的下載」跟「刪掉一筆已結束的紀錄」在操作上都是同一個「不要這筆了」的意圖，UI 也都會是同一顆按鈕，拆成兩支 API 除了語意上稍微乾淨一點，沒有實際好處。

## Consequences

- `JobStore` 需要新增一個真正執行 `DELETE FROM download_jobs` 的方法，跟既有 `cancel()`（`UPDATE` 成 `cancelled`）分開，因為終態的紀錄應該從表格裡整筆消失，不是變成另一種「已取消」狀態。
- `DELETE /api/downloads/:id` 的回應語意變得比較「重載」（同一個狀態碼可能代表取消或刪除），呼叫端（前端）要自己決定要顯示「已取消」還是「已刪除」的後續反應，而不是完全依賴回應內容判斷。
- 沒有清掉的磁碟殘留（`failed` 的 cache、被刪除紀錄但檔案還在 `DOWNLOADS_DIR` 的 `completed`）會持續累積，長期需要使用者自己手動清或另外做一個「清理孤兒檔案」的功能，這次不處理。
